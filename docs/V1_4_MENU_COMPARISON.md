# v1.4 Menu Comparison Contract

## Purpose

v1.4 unlocks scientifically defensible counterfactual comparison for **Passing Corridors** and the **Action Menu composite**.

The release answers a narrower question than causal football analysis:

> If one off-ball teammate is placed farther along the run implied by their focal-state velocity, how does the authoritative model-derived action menu change when candidates are regenerated from that altered state?

This is a synthetic teaching intervention over an illustrative showcase state. It is not observed future truth, a causal estimate, or a claim about real player intent.

## Governing invariant

The central v1.4 rule is:

> No Condition B candidate value may reuse a candidate score generated from Condition A state.

Condition B candidates must be generated independently by Python `AffordanceEngine` from the alternative frame produced by the frozen earlier-run intervention.

## Two scientific lanes

The comparison workbench exposes four channels, but they belong to two different evidence lanes.

```text
STATE-ONLY

Future Space
Option Creation

A options = []
B options = []

REGENERATED

Passing Corridors
Action Menu

A options = frozen authoritative showcase candidates
B options = independently regenerated AffordanceEngine candidates
```

The TypeScript API encodes this distinction as a discriminated union. `passing_corridors` and `menu` cannot be constructed through `buildVolumeComparison()` without both the validated counterfactual artifact and the authoritative current showcase options.

## Authoritative regeneration chain

The scientific path is:

```text
focal FrameState
    |
    +-> Condition A authoritative ActionOption table
    |
    +-> earlier-run intervention
            |
            +-> alternative FrameState
                    |
                    +-> Python AffordanceEngine.generate()
                            |
                            +-> Condition B ActionOption table
```

The frontend does not port the full option-scoring engine into TypeScript. It consumes the frozen artifact generated by `showcase-build`.

## Frozen artifact

Each scenario exposes:

```text
scenarios/<scenario_id>/counterfactual_options.json
```

The artifact includes:

- schema version;
- scenario and focal-frame identity;
- focal timestamp;
- lead presets `0.50`, `0.75`, and `1.00 s`;
- Condition A baseline candidates;
- regenerated Condition B candidates;
- earlier-run intervention metadata;
- semantic candidate comparisons;
- candidate support partition;
- generator name and module;
- package version;
- effective generator configuration fingerprinted by SHA-256;
- candidate identity contract;
- intervention contract;
- literal `future_observed_frames_used=false`.

Unavailable interventions are explicit and are never represented as a successful empty regenerated menu.

## Semantic candidate identity

Cross-condition identity is independent of target coordinates.

```text
pass:<target_player_id>
carry:<signed_angle_offset_deg>
hold
```

This allows a pass candidate to remain the same semantic action when the runner moves and the pass target coordinate changes.

A candidate comparison is classified as one of:

- shared between A and B;
- A-only;
- B-only.

A numerical score delta exists only for shared semantic candidates. One-sided candidates keep `null`, not a fabricated zero.

## Frontend validation gate

Before regenerated candidate evidence is exposed to the volume engine, the resolver validates:

1. artifact scenario matches the focal frame sequence;
2. artifact frame exists for the focal frame ID;
3. artifact timestamp matches the focal frame timestamp;
4. the requested lead is one of the frozen presets;
5. the artifact condition is available;
6. browser and Python intervention IDs match;
7. moved player identity matches;
8. lead, speed, displacement, origin, and destination match within the frozen numerical tolerance;
9. Condition A candidates exactly match the currently loaded showcase options after semantic indexing;
10. candidate identities remain unique;
11. generator provenance survives transport;
12. the no-future-observed-frame contract remains literal false.

Any mismatch fails closed before a regenerated B scene is built.

## Volume construction

The existing `buildAffordanceVolume()` implementation remains the volume authority.

v1.4 does not introduce a second Menu formula.

For regenerated channels:

```text
Condition A scene = buildAffordanceVolume(focal frame, A candidates, config)
Condition B scene = buildAffordanceVolume(alternative frame, B candidates, config)
```

Both scenes use the same:

- channel;
- deterministic quality level;
- threshold;
- horizon;
- voxel budget;
- pitch dimensions;
- support/difference algebra.

The v1.3 state-only path remains unchanged and still passes `options=[]` on both sides.

## Support semantics

The difference algebra keeps the v1.3 rule:

> not retained is not zero.

Shared retained support may have a numerical `B-A` delta.

A-only and B-only support are categorical. They are rendered as distinct rails and never converted into zero-valued cells.

This matters at two levels in v1.4:

- voxel support can be A-only or B-only;
- action candidates can be A-only or B-only.

Those are related but distinct scientific facts.

## Candidate-local forensics

An inspected regenerated cell can expose the exact candidate contributions that produced the local field value on each side.

Each contribution includes:

- `optionId`;
- candidate kind;
- geometric score;
- local spatial contribution.

This supports interpretations such as:

> The local corridor changed because the same semantic pass moved to a different target and score under Condition B.

or, in later candidate birth/death work:

> A candidate existed only on one side of the intervention.

The UI must not convert this into causal language.

## Reproducible URL state

The comparison route remains:

```text
/volume/compare
```

A citable state encodes:

- `scenario`;
- focal frame index `fi`;
- `cmp=earlier-run`;
- `lead`;
- channel `dc`;
- deterministic quality `dq`;
- retention threshold `dt`;
- temporal mode and slice/band parameters.

`dc` now accepts:

```text
future_space
option_creation
passing_corridors
menu
```

The UI labels the first two as `STATE` and the latter two as `REGENERATED`.

## Forensic JSON contract

The inspector export schema is:

```text
1.4.0-d
```

A state-only export records:

```text
candidateOptionsIncluded = false
candidateOptionsRegenerated = false
candidateEvidence.mode = state_only
```

A valid regenerated export records:

```text
candidateOptionsIncluded = true
candidateOptionsRegenerated = true
candidateEvidence.mode = regenerated_counterfactual_candidates
generator.name = AffordanceEngine
generator.configSha256 = <64 hex chars>
```

It also preserves:

- source evidence status;
- intervention identity and geometry;
- support category;
- numerical delta only when valid;
- one-sided-presence-not-zero boundary;
- no interpolation boundary;
- not-calibrated-probability boundary;
- no-future-observed-frame boundary.

The serializer independently verifies that the evidence lane matches the requested channel. `menu` or `passing_corridors` with state-only evidence fails closed, and `future_space` or `option_creation` with regenerated evidence fails closed.

## Failure behavior

Regenerated comparison must fail closed when any of the following occurs:

- artifact missing;
- artifact malformed;
- wrong scenario;
- wrong frame or timestamp;
- unavailable lead;
- wrong intervention geometry;
- baseline candidate drift;
- duplicate semantic identity;
- stale generator/config provenance;
- invalid support accounting;
- a regenerated channel is asked to export state-only evidence;
- a state-only channel is asked to export regenerated evidence.

The workbench must not silently fall back to stale Condition A candidates.

## Claim boundary

v1.4 can claim:

- Condition B candidate menus are independently regenerated by the authoritative Python engine;
- semantic candidate identity is stable across target movement;
- Passing Corridors and Menu use separate A/B candidate tables;
- stale or mismatched regenerated evidence fails closed;
- one-sided candidate and voxel support remains categorical;
- forensic exports preserve generator/config/intervention provenance;
- no future observed frame is used by the intervention or regenerated-menu comparison.

v1.4 cannot claim:

- causal effects;
- observed future truth;
- observed player intent;
- expert-labeled action availability;
- calibrated probabilities;
- empirical superiority of one model or intervention.

Those remain downstream evidence questions.

## Next release candidate

The natural v1.4 release-candidate extension is **Candidate Birth/Death**.

The visual grammar should distinguish:

```text
candidate survives -> score/target changes
candidate moves    -> corridor bends
candidate disappears -> A-only
candidate appears    -> B-only
```

Birth/death language should be displayed only when the authoritative A/B semantic candidate sets are actually asymmetric.

That extension should reuse the current validated regeneration artifact and evidence lanes rather than weakening them.
